# Screen Inventory and Delivery Contracts

## Contract applied to every screen

Every record below inherits these explicit requirements: native Stack header unless marked launch;
Poppins and semantic theme tokens; 48dp targets; screen-reader order/labels/states; dynamic type and
non-color status; safe-area/keyboard behavior; authenticated/role/organization/branch/permission
guards described by the record; analytics with opaque identifiers and no PII; allowlisted deep
links; no notification navigation until session and guards resolve; safe errors with trace IDs;
loading/empty/error/offline/cached/refresh/pagination behavior stated per class; and tests for route,
access, themes, accessibility, happy path, and every applicable state. All statuses are `NOT STARTED`
unless explicitly identified as foundation work. A screen is done only when real navigation/data,
states, permissions, tests, analytics hooks, security review, documentation, and roadmap updates are
complete; hardcoded product data cannot be marked complete.

### Class defaults

- **Static/local:** no backend/database/seed dependency; no loading/pagination/refresh; offline fully
  available; errors limited to device capability/persistence; content changes require app release.
- **Form:** React Hook Form + Zod; disable while submitting; one intent per press; retain safe values
  on recoverable error; focus/announce first error; backend field/global errors; retry only after a
  definite failure. Sensitive forms do not persist. Exact fields below remain product/backend review.
- **List:** TanStack Query; cursor pagination; server search/filter/sort when scale warrants; pull to
  refresh; skeleton first load; dedicated no-data and no-results states; cached stale/offline banner;
  retryable error; FlashList when expected volume/performance justifies it.
- **Detail:** fetch by opaque ID; skeleton, not-found/removed, authorization, error, stale/offline and
  refresh states; permission-gated actions; related records paginated; audit data when financial or
  administrative.
- **Financial mutation:** online only; backend authorization, transaction PIN if required,
  idempotency key, confirmation summary, pending/success/failure/unknown outcome, no blind retry,
  ledger/audit record, and duplicate-submission test.

## Required screens inferred but absent from the prototype

These are **BLOCKED** pending product/backend confirmation: notification list/detail/preferences;
wallet fund/send/withdraw plus payment callback; transaction detail/receipt; contribution checkout
and result; linked bank accounts; edit profile; KYC status/remediation; security/session/device settings;
theme settings; referral share; platform fees; support hub/conversation; account blocked,
session expired, maintenance, and global offline recovery. Each must receive a full record using this
contract before implementation. Organization, branch, member administration, approvals, and
documents are not evidenced by the reference and must not be invented solely from the initial brief.
